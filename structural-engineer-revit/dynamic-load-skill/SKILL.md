# Dynamic Load

## What this actually is

Same two-stage split `revit-load-application` used, applied to lateral loads instead of gravity: **what's the load** (a code lookup and a formula — zone coefficient, site class, the design response spectrum equation, the base shear and velocity pressure formulas) and **where does it go** (also mostly a code formula here, not a geometry problem — Eq 6.2.41's height-weighted vertical distribution spreads base shear to story forces; Fig 2.4.6/2.4.10's pressure-coefficient tables spread velocity pressure to windward/leeward/side/roof zones). `codes/bnbc2020/seismic.py` and `codes/bnbc2020/wind.py` answer "what's the load"; the same two modules also carry "where does it go" (`vertical_distribution()`, the `*_CP`/`GCPF` tables) since, unlike gravity's tributary-area geometry problem, this stage's distribution really is just more code. `scripts/apply_dynamic_loads.py` is the orchestrator.

**Every value here was checked directly against the actual BNBC 2020 text — not recalled — with the same discipline `revit-load-application`'s `loads.py` used.** One necessary exception, flagged loudly where it happens: the design response spectrum equations (Eq 6.2.35a-d) survived PDF text extraction badly mangled, and were reconstructed as the standard Eurocode-8 Type-1 shape BNBC's own S/TB/TC/TD/η notation is drawn from, then verified continuous at every branch boundary with sympy (`codes/bnbc2020/seismic.py`'s module docstring has the full reasoning). That's a documented, checked reconstruction, not a guess — but it's still worth a final spot-check against a clean copy of the code before it's load-bearing on a stamped drawing.

## Why story-level distribution is right here (and individual-element distribution isn't)

`revit-structure-recognition`'s own SKILL.md already makes this point once, for the same reason it applies again here: **stiffness governs how lateral load actually splits between individual walls and frames at a story, and this skill doesn't do that.** Eq 6.2.41's vertical distribution — spreading base shear up the building by height and weight — is a code-mandated, purely geometric formula at the *story* (diaphragm) level, no stiffness needed, squarely in scope. Splitting a story's shear *within* that story, across several shear walls or frames of different relative rigidity, is a different problem that genuinely needs a stiffness matrix — `structural-analysis`'s job once it exists, the same boundary `revit-load-application` already drew for gravity's tributary-vs-stiffness split. This skill's output stops at story force `Fx` and story shear `Vx`; handing that down to individual vertical elements is out of scope here on purpose.

## Workflow

**1. Assemble `site_seismic_wind_input.json`.** None of this — seismic zone, site soil class, chosen lateral system per direction, wind exposure category, enclosure classification — lives in the Revit model or in `structural_model.json`; it's classification and site judgment only an engineer supplies, the same way `revit-load-application` needs an `occupancy_map.json` for data Revit doesn't carry either. See `references/site_seismic_wind_input_format.md` for the full shape, including why `story_seismic_weights` is a required input here rather than something re-aggregated automatically from `revit-load-application`'s own panel-level output.

**2. Run the pipeline.**
```bash
python3 scripts/apply_dynamic_loads.py --structural-model structural_model.json \
    --site-input site_seismic_wind_input.json --out /path/to/output_dir
```
This reads the stories already in `structural_model.json`, computes the equivalent-static seismic procedure for each orthogonal direction independently and the MWFRS wind pressure chain, and writes the enriched model back out with `dynamic_loads` populated.

**3. Open both `needs_review` lists before trusting either half.** `dynamic_loads.seismic.needs_review` and `dynamic_loads.wind.needs_review` are independent — a project can come back with fully computed seismic and a wind section that's entirely flagged (the common case today, until the wind tables below are sourced), or vice versa. A structural system that isn't code-permitted at the site's actual Seismic Design Category raises loudly (`get_structural_system()` raises rather than returning a number) rather than silently producing an `R` the code doesn't allow there.

**4. Keep every direction and every load type separate all the way through.** X and Y direction results are never merged (they can legitimately have different systems, periods, and base shears), and seismic weight's `DL`/`SDL`/`LL` components stay unsummed inside `seismic_weight_kn()` the same way `revit-load-application` never pre-sums them — factored load combinations are still `structural-design`'s job, and BNBC's own combinations (Sec 2.5.13) aren't transcribed here yet regardless (see Known Limitations).

## Response spectrum, time history, and pushover: where the line is

BNBC's own Sec 2.5.8-2.5.12 lay out four analysis paths beyond the equivalent-static procedure: response spectrum analysis (RSA), linear time history (LTHA), nonlinear time history (NTHA), and nonlinear static/pushover (NSA). All four need something this skill doesn't have: RSA and the time-history methods need actual modal properties (periods, mode shapes, participation factors) from an eigenvalue solve of the real stiffness matrix; NSA needs a full nonlinear pushover solve. Running that solve is `structural-analysis`'s job (openseespy is available and confirmed working in this environment), not this one's — the same load-application-vs-analysis boundary that kept full FEA out of `revit-load-application`. `structural_model.json` doesn't carry parsed numeric section/material properties yet either (columns and framing carry a `section_hint` string like `"300x300"` and a `material.names` grade string like `"Concrete C30/37"` from `revit-structure-recognition` — real data, but needing light parsing into an actual stiffness matrix, which is squarely `structural-analysis`'s job to do, not this skill's).

What this skill *does* build, so `structural-analysis` runs the real solve against a verified spec rather than starting from nothing: for **each direction**, `dynamic_loads.seismic.<direction>.rsa` carries the full Sec 2.5.9 system — the design spectrum as ~200 portable `{T_sec, Sa_g}` points (`seismic.design_response_spectrum_curve()`, not just a formula another skill would need to reimplement), the 90%-mass-participation requirement, the SRSS/CQC modal combination rule (CQC required specifically where translational/torsional periods are closely spaced, per Sec 2.5.9.4's own words), and the force/displacement scaling rules tied back to the ESFP base shear already computed. `.ltha` carries Sec 2.5.10's verified ground-motion selection and scaling criteria (minimum 3 records, the exact 0.2T-1.5T matching window, the 2D vs. 3D matching rule, the <7-records-use-max/≥7-use-average design-value rule) — criteria, not actual selected/scaled records, which need a real ground-motion library and structural-analysis's real computed T. `.ntha` carries the same, plus the *unreduced* real design spectrum (R=1, I=1, per Sec 2.5.11.2) NTHA is run against. `shared_inputs.requires_3d_dynamic_model` (Sec 2.5.9.1) tells `structural-analysis` whether it needs one 3D model or two independent 2D ones. NSA (pushover) stays out of scope — it needs nonlinear member hinge behavior tied to final reinforcement design, a different, later kind of dependency than "needs an eigenvalue solve."

## Wind: what's verified and what still needs a real number

Section 2.4 doesn't exist at all in the same source PDF `revit-load-application` and this skill's own `seismic.py` were built from (confirmed by fetching it directly — it jumps straight from live loads to earthquake loads) — it was read from a second, independent source instead (`wind.py`'s module docstring has the citation). That source gave a complete, verified formula chain — velocity pressure, both the simplified and full gust factor paths, internal pressure coefficients, MWFRS wall and low-rise-roof pressure coefficients, the design pressure equations — plus the enclosure-classification inequalities, tested against three distinct scenarios (open/enclosed/partially-enclosed) in this skill's own build process.

What it didn't give: several of BNBC's own standard numeric tables (basic wind speed by location, velocity pressure exposure coefficient `Kz`, directionality factor `Kd`, wind importance factor) are referenced constantly in the source text but rendered as images, not extractable text — and a further search for a verified per-district basic wind speed table (matching the granularity this project's practice area needs — Cumilla, Chandpur specifically) came up short; only unverified division-level approximations turned up, and BNBC's zone contours are already known not to follow administrative division lines (Chandpur's own seismic `Z=0.20` differs from Chittagong's `0.28` despite sharing a division). Rather than guess, `apply_dynamic_loads.py` accepts these as explicit overrides in `site_seismic_wind_input.json` (`basic_wind_speed_v_ms_override`, `kz_by_story_override`, etc.) and flags `needs_review` wherever they're missing — the formula chain runs correctly and immediately the moment an engineer supplies verified values from a physical copy of the code.

## Known limitations

- **The actual RSA/LTHA/NTHA solve isn't run, and NSA (pushover) isn't in scope at all** — see the dedicated section above. This skill builds the complete, verified system (design spectrum as data, mass participation and modal combination rules, ground-motion selection/scaling criteria) for the first three; the eigenvalue/time-stepping solve itself needs `structural-analysis`'s real stiffness model.
- **Earthquake load combinations (Sec 2.5.13 — E, Eh, Emh, Ev) aren't transcribed.** Almost certainly structurally similar to ASCE 7's `E=Eh±Ev` treatment (BNBC's earthquake chapter is otherwise a close relative), but BNBC's own symbol list doesn't define a redundancy factor ρ anywhere, and its native spectral parameter is `Sa`, not ASCE 7's `SDS`/`SD1` split — so the ASCE formula must not be assumed to transplant unchanged. Get the actual section text before implementing this.
- **Allowable storey drift `Δa` (Sec 2.5.14) isn't transcribed.** `seismic.story_drift()` computes the demand side; there's currently nothing to check it against.
- **The masonry/shear-wall-specific period formula (Eq 6.2.39/6.2.40) isn't implemented** — came through too OCR-garbled to reconstruct responsibly, unlike the response spectrum (not a universally standardized shape to cross-check against). `approximate_period()` covers the general `Ct·hn^m` formula only — every named frame type, which covers this project's stated RCC/steel frame practice.
- **Non-structural components, seismic isolation, soft-storey design, and non-building structures (Sec 2.5.15-2.5.18) are out of scope** — niche relative to ordinary frame buildings.
- **Wind's C&C (components and cladding) pressures aren't computed, and the roof `GCpf` table is transcribed for the flat/near-flat 0-5° case only** — MWFRS wall pressures (the primary lateral-system driver) are the focus; cladding design and other roof-angle rows are future work.
- **Seismic weight is an engineer-supplied input (`story_seismic_weights`), not auto-aggregated from `revit-load-application`'s own output** — a deliberate architectural choice, not an oversight: that skill's `loads.panels` stores per-*beam* reaction-equivalents, and re-deriving a per-story total from them risks double-counting at every interior beam; reaching into a separately-packaged skill's occupancy tables directly would be fragile. See `references/site_seismic_wind_input_format.md` for the reasoning.
- **Building irregularity isn't classified** — `is_regular` is an engineer-supplied input, since `revit-structure-recognition` doesn't classify Sec 2.5.5.3's irregularity types yet. Get this wrong and a building that actually needs mandatory dynamic analysis could be waved through on the ESFP path alone.
